1. Executive Summary

The SSM-Score Manipulation Attack targets Reliable-dRAG's on-chain Scoring & Sampling Mechanism. All blockchain private keys are the publicly-known Hardhat defaults, so an attacker impersonates the LLM service and submits forged score-update transactions that inflate a malicious source's on-chain Ri/Ui by 500×. The system then exclusively selects the poisoned source, dropping accuracy from 42.9% → 0%.

How SSM Scoring Normally Works

After each query the LLM service evaluates answer correctness and calls feedbackAndUpdateScoreRecords() on the smart contract, updating each source's Ri and Ui. The sampling function uses Ui as weights — sources with higher scores are selected more often. The blockchain makes this audit trail immutable.

3. Vulnerability Analysis

VULN-01 · Exposed Default Private Keys (Root Cause)

All accounts use publicly documented Hardhat test keys committed to the repo. Anyone reading the config files gets the LLM service's private key — the sole authorised caller of feedbackAndUpdateScoreRecords().

VULN-02 · Unconstrained Score Delta

The contract accepts arbitrary absolute score values with no max delta, no rate limiting, and no sanity check. One call can raise a score from 10,000 to 1,009,999 — a 100× jump with zero on-chain resistance.

VULN-03 · Self-Signature Acceptance

The contract validates that an update is signed by the source being scored. But because the attacker controls that source's private key (VULN-01), they manufacture valid signatures for fake messages with no real query occurring.

What the Blockchain DOES Protect Against

The contract correctly prevents unauthorised parties (those lacking the LLM service key) from submitting updates, and maintains an immutable on-chain audit trail. These protections hold in a properly key-managed deployment — they fail here solely because default test keys were never rotated.

10. Recommendations

Fix VULN-01 — Proper Key Management

Replace Hardhat default keys with randomly generated keys stored in environment variables or a secrets manager. Never commit private keys to source control.

Fix VULN-02 — Score Delta Cap in Smart Contract

Add a max delta per transaction (e.g., ±1,000) and a per-source cooldown period to feedbackAndUpdateScoreRecords().

Fix VULN-03 — Multi-Signature Requirement

Require M-of-N signatures from different data sources before accepting a score update. A single self-signed message from the target source should never be sufficient proof.
