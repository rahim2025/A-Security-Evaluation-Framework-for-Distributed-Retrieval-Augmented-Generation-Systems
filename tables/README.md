## Notes

- **KB Extraction**: `Authorized` vs `Authorized-Blind` compares probing with vs. without ground-truth-guided targeting. `LLM Interface` is the black-box `/query` probing phase (CRR = chunk_recovery_rate, per `Reliable-dRAG.md` metric conventions). The `Unauthorized` phase (API-key gate enforced, 0 docs, HTTP 401 on every source) is no longer a row in this CSV — every metric in it was 0 or n/a, so it was dropped from the table. That result still exists: it's reported in `reports/kb.md` and the raw `attack_logs/kb_extraction/*.json` logs (`phase_a_unauth`).
- **MIA**: now covers all three strategies implemented in `attack/Mia_attack/`, not just the single-signal production run (see the earlier session finding that only one of three was being exercised):
  - **Production (thesis multi-seed)**: `run_attack.py`, gated composite (`decision_match` weight=1.0, others=0.0 — the empirically-tuned Revision-6 winner, not a partial config), n=25/25, seeds 0/42/123 per `.claude/CLAUDE.md`'s minimum-seed requirement. AUC-ROC 0.62 / 0.58 / 0.50, mean 0.567 ± 0.061 — a real (if modest) signal on 2 of 3 seeds, unlike the earlier single-seed run (seed 999, n=5/5, AUC 0.50) kept in the table for reference only.
  - **Ablation-eval (held-out seeds)**: `run_ablation_eval.py`, the diagnostic comparison of the production composite vs. an ablation composite vs. positional/adaptive/semantic decision-match variants, on the documented 10-seed held-out list from Revision 6. Mean AUC ≈ 0.52 across the board (includes chance) — consistent with `reports/MIA_Security_Analysis_Report.md`'s conclusion that the full composite doesn't generalize to held-out seeds. Note: adaptive and semantic decision-match land identical to the positional check on every seed here (undefended responses never phrase around the opening words), matching the report's Revision 6 finding.
  - **Consistency-score pilot** (`mia_consistency_results.csv`): `run_consistency_pilot.py`, repeated-probe majority-agreement signal, 6 seeds (3 original + 3 fresh). Mean AUC ≈ 0.55 — weak, inconsistent signal (seed 0 alone reached 0.75; the 3 newest seeds are flat at 0.50 with degenerate 1.00/1.00 consistency, i.e. every probe agreed for both members and non-members — no discriminative signal on those seeds).
  - **Bug fixed while running this**: `run_attack.py` was crashing with `UnicodeEncodeError` (Windows console can't print a `←` glyph) *after* computing results but *before* saving them — silently discarding a full run's live LLM calls. Fixed by forcing UTF-8 on stdout/stderr at the top of the script; first attempt at seeds 0/42/123 was lost to this bug and had to be re-run.
  - Per-seed values for the ablation-eval are **not** expected to exactly reproduce prior runs of the same seed (e.g. `reports/MIA_Security_Analysis_Report.md`'s seed 7/13 numbers) — the LLM service's generation isn't fully deterministic even with a fixed sampling seed, so some run-to-run variance is real, not a bug.
- **SFA**: the live run only exercised one config (`high_connectivity`, ratio 0.3) as a real-network validation smoke test — note it shows `hit_rate=1.00` despite `drop_rate=1.00`, i.e. all 200 drops were recovered via redundant-probe rerouting rather than causing an unanswered query. The mock sweep (11 rows) is the fuller baseline/random/high_connectivity comparison and is the same-day companion run.
- **SSM-Score**: two structurally distinct attacks, reported as separate `Attack` values rather than averaged into one row set — see `reports/SSM_Score_Attack_Explained.md` and `reports/Security_Analysis_Report.md` §12.1 for the full mechanism writeup.
  - **`grounding_farming`** (flagship, no privileged access): a data source farms undeserved reliability/usefulness credit by exploiting the orchestrator's naive substring-based grounding check — no blockchain interaction, no key beyond the source's own. `Engagement Rate` is `farm_source_in_importance_score` (fraction of rounds the farming source survived the reliability-weighted rerank into the final top-k) — the non-degenerate misdirection signal for this 3-source topology. **Do not average these three rows**: the result is genuinely bimodal (1/3 seeds fully escalate, 2/3 stay flat), driven by a self-reinforcing feedback loop that only triggers if an early "grounded" credit lands by chance — averaging would produce a number describing none of the three actual outcomes. `R/U Gap vs Comparison` is measured against the untouched `sources_20`.
  - **`key_forgery`** (secondary, orchestrator-key-compromise): forges a score-update transaction using the LLM orchestrator's own private key. Requires far higher privilege than `grounding_farming` but is deterministic — `Engagement Rate` (`rounds_accepted_fraction`) is `1.0` in all 3 seeds tested, i.e. every round accepted, every time. Parameters (`Amplify=4000`, `Inter-Round Delay=2.5s`) are deliberately chosen just inside the deployed on-chain defense's `MAX_DELTA_PER_UPDATE=5,000`/`MIN_UPDATE_INTERVAL=2s` caps — the original reckless defaults (`Amplify=999,999`, 0.5s) revert on round 1 and are not represented in this table (see the Security Analysis Report §8.1 for that comparison). `R/U Gap vs Comparison` is `n/a` because this variant was not evaluated against a parallel untouched-source baseline the way `grounding_farming` was.
  - Both attacks target `sources_100` and were run with a freshly-restarted, confirmed-pristine chain (10000/10000 all sources) before each seed, so cross-seed and cross-attack comparisons are not confounded by leftover state.
- **DDoS**: `mock` rows are network-level impact (hit_rate/availability/node overload) — each row is the mean over 5 attack waves x 3 seeds (0, 42, 123) per (strategy, ratio); `random`/`sequential`/`targeted` are node-selection strategies, ratio is the fraction of peers targeted. `live` rows are the companion real-Docker-network run (seed 42 only) reporting answer-quality degradation (EM/F1/semantic similarity) at low/mid/high flood intensity, each as a baseline-vs-post_attack pair — this is the direct DDoS analogue of the sample poison-ratio-vs-F1 table. `targeted`/high-intensity `live` `post_attack (high)` is the worst case (F1 0.0, 90% query failure).
  - **`Avg Hops/Query` vs. `Avg Messages`, do not conflate these:** `Avg Hops/Query` is the real per-query hop count for both modes. `Avg Messages` is `run_live_evaluation.py`'s neighbour-notify overhead *estimate* for live rows only (`= avg_hops × num_query_neighbor`, currently 2) — it is not a separately-measured quantity, and it is exactly 2x `Avg Hops/Query` on every live row by construction. A `live` `Avg Hops/Query` column used to be blank (`n/a`) here, which is what caused an earlier version of the thesis table to pull `Avg Messages` and mislabel it "Avg Hops" (2.00/4.00/6.00/6.00 instead of the real 1.00/2.00/3.00/3.00 at baseline/low/mid/high) — fixed by populating `Avg Hops/Query` directly from the source log's `avg_num_hops` field for every live row.
  - **`F1` is on the same 0–1 fraction scale as `Exact Match`/`Semantic Similarity`**, not percent (an earlier version of this CSV stored `F1` as 0–100 — e.g. `60.00` next to `Exact Match=0.60` — while every other unlabeled-`%` column in this table is a 0–1 fraction; fixed for consistency).
- All values pulled directly from JSON/CSV logs, no re-computation. Regenerate by re-running the attacks and re-pointing at the newest file in each `attack_logs/<attack>/` subfolder.
